[X.509](https://en.wikipedia.org/wiki/X.509) est un format standard pour les certificats de clé publique émis par une Infrastructure à Clé Publique (PKI) publique ou privée. Les certificats X.509 personnels sont utilisés à des fins d'authentification ou de signature, comme S/MIME (Secure/Multipurpose Internet Mail Extensions). Cependant, Git prend également en charge la signature des commits et des tags avec des certificats X.509, de manière similaire à [GPG (GnuPG, ou GNU Privacy Guard)](gpg.md). La principale différence réside dans la façon dont GitLab détermine si la signature du développeur est approuvée ou non :

- Pour X.509, une autorité de certification racine est ajoutée au magasin de confiance GitLab. (Un magasin de confiance est un dépôt de certificats de sécurité approuvés.) Combiné avec les certificats intermédiaires requis dans la signature, le certificat du développeur peut être relié à un certificat racine approuvé.
- Pour GPG, les développeurs [ajoutent leur clé GPG](gpg.md#add-a-gpg-key-to-your-account) à leur compte.

GitLab utilise son propre magasin de certificats et définit donc la [chaîne de confiance](https://www.ssl.com/article/what-is-a-certificate-authority-ca/). Pour qu'un commit ou un tag soit vérifié par GitLab :

- L'e-mail du certificat de signature doit correspondre à une adresse e-mail vérifiée dans GitLab.
- L'instance GitLab nécessite une chaîne de confiance complète depuis le certificat de la signature jusqu'à un certificat approuvé dans le magasin de certificats GitLab. Cette chaîne peut inclure des certificats intermédiaires fournis dans la signature. Vous devrez peut-être ajouter des certificats, tels que des certificats racine d'autorité de certification, [dans le magasin de certificats GitLab](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates).
- L'heure de signature doit être comprise dans la plage temporelle de la [validité du certificat](https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5), qui est généralement de trois ans au maximum.
- L'heure de signature est égale ou postérieure à l'heure du commit.

> [!note]
> Si un certificat racine CA ou un certificat intermédiaire de la chaîne de confiance expire et est renouvelé, les commits peuvent temporairement s'afficher comme « non vérifiés » jusqu'à ce que vous les [re-vérifiez](#re-verify-commits).

Si le statut d'un commit a déjà été déterminé et stocké dans la base de données, utilisez la tâche Rake [pour revérifier le statut](../../../../administration/raketasks/x509_signatures.md). GitLab vérifie quotidiennement les listes de révocation de certificats avec un worker d'arrière-plan.

## Problèmes connus {#known-issues}

- Les certificats sans `authorityKeyIdentifier`, `subjectKeyIdentifier` et `crlDistributionPoints` s'affichent comme **Non vérifié**. Nous recommandons d'utiliser des certificats d'une PKI conformes à la norme [RFC 5280](https://www.rfc-editor.org/info/rfc5280/).
- Le badge **Vérifié** n'est pas affiché sur l'offre GitLab.com, car [l'importation d'une autorité de certification (CA) personnalisée](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates) est uniquement disponible pour GitLab Self-Managed.
- La définition de valeurs dans la section Extended Key Usage (EKU) de votre certificat, en plus du Key Usage (KU) requis de `Digital Signature`, est susceptible de provoquer l'affichage de vos commits comme **Non vérifié**. Pour résoudre ce problème, ajoutez `emailProtection` à votre liste EKU. La RFC 5280 spécifie cette limitation.

  Pour diagnostiquer le problème, suivez la procédure [Vérification S/MIME avec OpenSSL](#smime-verification-with-openssl).
- Dans GitLab 16.2 et versions antérieures, si vous avez plusieurs adresses e-mail dans la liste Subject Alternative Name de votre certificat de signature, [seule la première est utilisée pour vérifier les commits](https://gitlab.com/gitlab-org/gitlab/-/issues/336677).

## Configurer pour les commits signés {#configure-for-signed-commits}

Pour signer vos commits, vos tags, ou les deux, vous devez :

1. [Obtenir une paire de clés X.509](#obtain-an-x509-key-pair).
1. [Associer votre certificat X.509 à Git](#associate-your-x509-certificate-with-git).
1. [Signer et vérifier les commits](#sign-and-verify-commits).
1. [Signer et vérifier les tags](#sign-and-verify-tags).

### Obtenir une paire de clés X.509 {#obtain-an-x509-key-pair}

Si votre organisation dispose d'une Infrastructure à Clé Publique (PKI), cette PKI fournit une clé S/MIME. Si vous ne disposez pas d'une paire de clés S/MIME d'une PKI, créez votre propre paire auto-signée ou achetez-en une.

### Associer votre certificat X.509 à Git {#associate-your-x509-certificate-with-git}

Pour profiter de la signature X.509, vous avez besoin de Git 2.19.0 ou version ultérieure. Vous pouvez vérifier votre version de Git avec la commande `git --version`.

Si vous disposez de la version correcte, vous pouvez procéder à la configuration de Git.

{{< tabs >}}

{{< tab title="Linux" >}}

Configurez Git pour utiliser votre clé de signature :

```shell
signingkey=$( gpgsm --list-secret-keys | egrep '(key usage|ID)' | grep -B 1 digitalSignature | awk '/ID/ {print $2}' )
git config --global user.signingkey $signingkey
git config --global gpg.format x509
```

{{< / tab >}}

{{< tab title="Windows et macOS" >}}

Pour configurer Windows ou macOS :

1. Installez [S/MIME Sign](https://github.com/github/smimesign) en suivant l'une des méthodes suivantes :
   - Téléchargez le programme d'installation.
   - En exécutant `brew install smimesign` sur macOS.
1. Obtenez l'identifiant de votre certificat en exécutant `smimesign --list-keys`.
1. Définissez votre clé de signature en exécutant `git config --global user.signingkey <ID>`, en remplaçant `<ID>` par l'identifiant du certificat.
1. Configurez X.509 avec cette commande :

   ```shell
   git config --global gpg.x509.program smimesign
   git config --global gpg.format x509
   ```

### Signer et vérifier les commits {#sign-and-verify-commits}

Après avoir [associé votre certificat X.509 à Git](#associate-your-x509-certificate-with-git), vous pouvez signer vos commits :

1. Lorsque vous créez un commit Git, ajoutez l'indicateur `-S` :

   ```shell
   git commit -S -m "feat: x509 signed commits"
   ```

1. Effectuez un push vers GitLab et vérifiez que vos commits sont signés avec l'indicateur `--show-signature` :

   ```shell
   git log --show-signature
   ```

1. *Si vous ne souhaitez pas saisir l'indicateur `-S` à chaque commit,* exécutez cette commande pour que Git signe vos commits à chaque fois :

   ```shell
   git config --global commit.gpgsign true
   ```

### Signer et vérifier les tags {#sign-and-verify-tags}

Après avoir [associé votre certificat X.509 à Git](#associate-your-x509-certificate-with-git), vous pouvez commencer à signer vos tags :

1. Lorsque vous créez un tag Git, ajoutez l'indicateur `-s` :

   ```shell
   git tag -s v1.1.1 -m "My signed tag"
   ```

1. Effectuez un push vers GitLab et vérifiez que vos tags sont signés avec cette commande :

   ```shell
   git tag --verify v1.1.1
   ```

1. *Si vous ne souhaitez pas saisir l'indicateur `-s` à chaque tag,* exécutez cette commande pour que Git signe vos tags à chaque fois :

   ```shell
   git config --global tag.gpgsign true
   ```

## Dépannage {#troubleshooting}

Pour les personnes qui effectuent des commits sans accès administrateur, consultez la liste des [problèmes de vérification avec les commits signés](_index.md#fix-verification-problems-with-signed-commits) pour trouver des solutions possibles. Les autres suggestions de dépannage présentes sur cette page nécessitent un accès administrateur.

### Re-vérifier les commits {#re-verify-commits}

GitLab stocke le statut des commits vérifiés dans la base de données. Vous pouvez re-vérifier les commits après :

- Le renouvellement d'un certificat racine CA ou intermédiaire.
- Des modifications apportées au magasin de certificats.

Pour re-vérifier les commits :

1. Assurez-vous que le certificat racine CA et les certificats intermédiaires éventuels se trouvent dans le magasin de certificats GitLab.
1. Exécutez la [tâche Rake `update_signatures`](../../../../administration/raketasks/x509_signatures.md) pour vérifier et mettre à jour le statut des commits précédemment vérifiés.

### Vérifications de validation principales {#main-verification-checks}

Le code effectue [ces vérifications clés](https://gitlab.com/gitlab-org/gitlab/-/blob/v14.1.0-ee/lib/gitlab/x509/signature.rb#L33), qui doivent toutes renvoyer `verified` :

- `x509_certificate.nil?` doit être false.
- `x509_certificate.revoked?` doit être false.
- `verified_signature` doit être true.
- `user.nil?` doit être false.
- `user.verified_emails.include?(@email)` doit être true.
- `certificate_email == @email` doit être true.

Pour déterminer pourquoi un commit s'affiche comme `Unverified` :

1. [Démarrez une console Rails](../../../../administration/operations/rails_console.md#starting-a-rails-console-session) :

   ```shell
   sudo gitlab-rails console
   ```

1. Identifiez le projet (par son chemin ou son identifiant) et le SHA complet du commit que vous analysez. Utilisez ces informations pour créer `signature` afin d'exécuter d'autres vérifications :

   ```ruby
   project = Project.find_by_full_path('group/subgroup/project')
   project = Project.find_by_id('121')
   commit = project.repository.commit_by(oid: '87fdbd0f9382781442053b0b76da729344e37653')
   signedcommit=Gitlab::X509::Commit.new(commit)
   signature=Gitlab::X509::Signature.new(signedcommit.signature_text, signedcommit.signed_text, commit.committer_email, commit.created_at, commit.project)
   ```

   Si vous apportez des modifications pour résoudre les problèmes identifiés lors des vérifications, redémarrez la console Rails et relancez les vérifications depuis le début.

1. Vérifiez le certificat sur le commit :

   ```ruby
   signature.x509_certificate.nil?
   signature.x509_certificate.revoked?
   ```

   Les deux vérifications doivent renvoyer `false` :

   ```ruby
   > signature.x509_certificate.nil?
   => false
   > signature.x509_certificate.revoked?
   => false
   ```

1. Exécutez une vérification cryptographique sur la signature. Le code doit renvoyer `true` :

   ```ruby
   signature.verified_signature
   ```

   S'il renvoie `false`, [approfondissez cette vérification](#cryptographic-verification-checks).

1. Confirmez que les adresses e-mail correspondent dans le commit et la signature :

   - La console Rails affiche les adresses e-mail comparées.
   - La commande finale doit renvoyer `true` :

   ```ruby
   sigemail=signature.__send__:certificate_email
   commitemail=commit.committer_email
   sigemail == commitemail
   ```

   Dans GitLab 16.2 et versions antérieures, [seul le premier e-mail](https://gitlab.com/gitlab-org/gitlab/-/issues/336677) de la liste `Subject Alternative Name` est comparé. Pour afficher la liste `Subject Alternative Name`, exécutez :

   ```ruby
   signature.__send__ :get_certificate_extension,'subjectAltName'
   ```

   Si l'adresse e-mail du développeur n'est pas la première de la liste, cette vérification échoue et le commit est marqué `unverified`.

1. L'adresse e-mail du commit doit être associée à un compte dans GitLab. Cette vérification doit renvoyer `false` :

   ```ruby
   signature.user.nil?
   ```

1. Vérifiez que l'adresse e-mail est associée à un utilisateur dans GitLab. Cette vérification doit renvoyer un utilisateur, par exemple `#<User id:1234 @user_handle>` :

   ```ruby
   User.find_by_any_email(commit.committer_email)
   ```

   Si elle renvoie `nil`, l'adresse e-mail n'est pas associée à un utilisateur et la vérification échoue.

1. Confirmez que l'adresse e-mail du développeur est vérifiée. Cette vérification doit renvoyer true :

   ```ruby
   signature.user.verified_emails.include?(commit.committer_email)
   ```

   Si la vérification précédente a renvoyé `nil`, cette commande affiche une erreur :

   ```plaintext
   NoMethodError (undefined method `verified_emails' for nil:NilClass)
   ```

1. Le statut de vérification est stocké dans la base de données. Pour afficher l'enregistrement de la base de données :

   ```ruby
   pp CommitSignatures::X509CommitSignature.by_commit_sha(commit.sha);nil
   ```

   Si toutes les vérifications précédentes ont renvoyé les valeurs correctes :

   - `verification_status: "unverified"` indique que l'enregistrement de la base de données doit être mis à jour. [Utilisez la tâche Rake](#re-verify-commits).

   - `[]` indique que la base de données ne contient pas encore d'enregistrement. Localisez le commit dans GitLab pour vérifier la signature et stocker le résultat.

#### Vérifications cryptographiques {#cryptographic-verification-checks}

Si GitLab détermine que `verified_signature` est `false`, recherchez la cause dans la console Rails. Ces vérifications nécessitent que `signature` existe. Reportez-vous à l'étape `signature` des précédentes [vérifications de validation principales](#main-verification-checks).

1. Vérifiez que la signature, sans vérifier l'émetteur, renvoie `true` :

   ```ruby
   signature.__send__ :valid_signature?
   ```

1. Vérifiez l'heure et la date de signature. Cette vérification doit renvoyer `true` :

   ```ruby
   signature.__send__ :valid_signing_time?
   ```

   - Le code autorise l'expiration des certificats de signature de code.
   - Un commit doit être signé pendant la période de validité du certificat, et à la date du commit ou après. Affichez l'heure du commit et les détails du certificat, notamment `not_before` et `not_after`, avec :

     ```ruby
     commit.created_at
     pp signature.__send__ :cert; nil
     ```

1. Vérifiez la signature, notamment que la confiance TLS peut être établie. Cette vérification doit renvoyer `true` :

   ```ruby
   signature.__send__(:p7).verify([], signature.__send__(:cert_store), signature.__send__(:signed_text))
   ```

   1. En cas d'échec, ajoutez les certificats manquants nécessaires à l'établissement de la confiance dans le [magasin de certificats GitLab](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates).

   1. Après avoir ajouté d'autres certificats (si ces étapes de dépannage réussissent), exécutez la tâche Rake pour [re-vérifier les commits](#re-verify-commits).

   1. Vous pouvez ajouter des certificats supplémentaires dynamiquement dans la console Rails pour vérifier si cela résout le problème.

      1. Retestez la signature avec un magasin de confiance `cert_store` modifiable. Elle doit toujours échouer, avec `false` :

         ```ruby
         cert_store = signature.__send__ :cert_store
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

      1. Ajoutez un certificat supplémentaire et retestez :

         ```ruby
         cert_store.add_file("/etc/ssl/certs/my_new_root_ca.pem")
         signature.__send__(:p7).verify([], cert_store, signature.__send__(:signed_text))
         ```

   1. Affichez les certificats inclus dans la signature :

      ```ruby
      pp signature.__send__(:p7).certificates ; nil
      ```

   1. [Des investigations supplémentaires peuvent être effectuées avec OpenSSL en ligne de commande](#smime-verification-with-openssl).

Assurez-vous que tous les certificats intermédiaires supplémentaires et le certificat racine sont ajoutés au magasin de certificats. Pour assurer la cohérence avec la façon dont les chaînes de certificats sont construites sur les serveurs web :

- Les clients Git qui signent des commits doivent inclure le certificat et tous les certificats intermédiaires dans la signature.
- Le magasin de certificats GitLab ne doit contenir que la racine.

Si vous supprimez un certificat racine du magasin de confiance GitLab, par exemple lorsqu'il expire, les signatures de commits qui remontent à cette racine s'affichent comme `unverified`.

#### Vérification S/MIME avec OpenSSL {#smime-verification-with-openssl}

En cas de problèmes avec la signature ou si la confiance TLS échoue, des investigations supplémentaires peuvent être effectuées avec OpenSSL en ligne de commande.

Exportez la signature et le texte signé depuis la [console Rails](../../../../administration/operations/rails_console.md#starting-a-rails-console-session) :

1. Les deux premières étapes des [vérifications de validation principales](#main-verification-checks) sont requises pour que `signature` ait été défini.
1. OpenSSL exige que les données au format PEM PKCS7 soient délimitées par `BEGIN PKCS7` et `END PKCS7`, ce qui nécessite généralement une correction :

   ```ruby
   pkcs7_text = signature.signature_text.sub('-----BEGIN SIGNED MESSAGE-----', '-----BEGIN PKCS7-----')
   pkcs7_text = pkcs7_text.sub('-----END SIGNED MESSAGE-----', '-----END PKCS7-----')
   ```

1. Écrivez la signature et le texte signé :

   ```ruby
   f1=File.new('/tmp/signature_text.pk7.pem','w')
   f1 << pkcs7_text
   f1.close

   f2=File.new('/tmp/signed_text.txt','w')
   f2 << signature.signed_text
   f2.close
   ```

Ces données peuvent maintenant être analysées en ligne de commande Linux à l'aide d'OpenSSL :

1. Le fichier PKCS #7 contenant la signature peut être interrogé :

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -print -noout
   ```

   La sortie doit inclure au moins une section `cert` ; il s'agit du certificat du signataire.

   La sortie contient beaucoup de détails de bas niveau. Voici un exemple de la structure et des en-têtes qui doivent être présents :

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
             issuer:
             validity:
               notBefore:
               notAfter:
             subject:
   ```

   Si les certificats de signature de code des développeurs sont émis par une autorité de certification intermédiaire, des détails de certificat supplémentaires doivent être présents :

   ```plaintext
   PKCS7:
     d.sign:
       cert:
           cert_info:
       cert:
           cert_info:
   ```

1. Extrayez le certificat de la signature :

   ```shell
   /opt/gitlab/embedded/bin/openssl pkcs7 -inform pem -print_certs \
       -in /tmp/signature_text.pk7.pem -out /tmp/signature_cert.pem
   ```

   Si cette étape échoue, le certificat du signataire est peut-être absent de la signature.

   - Corrigez ce problème sur le client Git.
   - L'étape suivante échouera, mais si vous copiez le certificat du signataire sur le serveur GitLab, vous pourrez l'utiliser pour effectuer des tests avec `-nointern -certfile signerscertificate.pem`.

1. Vérifiez partiellement le commit à l'aide du certificat extrait :

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify -certfile /tmp/signature_cert.pem -nointern
   ```

   La sortie inclut généralement :

   - Le commit parent
   - Le nom, l'e-mail et l'horodatage du commit
   - Le texte du commit
   - `Verification successful` (ou similaire)

   Cette vérification n'est pas identique à celle effectuée par GitLab, car :

   - Elle ne vérifie pas le certificat du signataire (`-noverify`)
   - La vérification est effectuée à l'aide du `-certfile` fourni plutôt que de celui contenu dans le message (`-nointern`)

1. Vérifiez partiellement le commit à l'aide du certificat contenu dans le message :

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt \
       -noverify
   ```

   Le résultat devrait être identique à celui de l'étape précédente, en utilisant le certificat extrait.

   Si le message ne contient pas le certificat, l'erreur inclut `signer certificate not found`.

1. Vérifiez entièrement le commit :

   ```shell
   /opt/gitlab/embedded/bin/openssl smime -verify -binary -inform pem \
       -in /tmp/signature_text.pk7.pem -content /tmp/signed_text.txt
   ```

   Si cette étape échoue, la vérification échoue également dans GitLab.

   Résolvez les erreurs éventuelles, par exemple :

   - `certificate verify error .. unable to get local issuer certificate` :
     - La chaîne de confiance n'a pas pu être établie.
     - Ce binaire OpenSSL utilise le magasin de confiance GitLab. Soit le certificat racine est absent du magasin de confiance, soit la signature ne contient pas les certificats intermédiaires et une chaîne vers une racine approuvée ne peut pas être construite.
       - Les certificats intermédiaires peuvent être placés dans le magasin de confiance s'il n'est pas possible de les inclure dans la signature.
       - [La procédure d'ajout de certificats](https://docs.gitlab.com/omnibus/settings/ssl/#install-custom-public-certificates) au magasin de confiance pour GitLab packagé - en utilisant `/etc/gitlab/trusted-certs`.
     - Testez des certificats approuvés supplémentaires avec OpenSSL en utilisant : `-CAfile /path/to/rootcertificate.pem`
   - `unsupported certificate purpose` :
     - Le certificat doit spécifier `Digital Signature` dans la section `X509v3 Key Usage` du certificat du signataire.
     - Si la section `X509v3 Extended Key Usage` (EKU) est spécifiée, elle doit inclure `emailProtection`. Consultez la [RFC 5280](https://datatracker.ietf.org/doc/html/rfc5280#page-44) pour plus de détails :

       > S'il n'existe aucun objectif compatible avec les deux extensions (Key Usage), le certificat ne doit être utilisé à aucune fin.

   - `signer certificate not found`, soit :
     - Vous avez ajouté l'argument `-nointern`, mais n'avez pas fourni `-certfile`.
     - Le certificat du signataire est absent de la signature.
